# Product — RFC Process

For any change that's cross-cutting, hard to reverse, or touches the Talent Algorithm.

## Why
Align on the *why* and the *approach* before code exists, in writing, in the open.

## How
1. Open an issue with the `rfc` label using the RFC template.
2. Structure: **Summary · Problem & goals (and non-goals) · Proposal · Alternatives · Risks & rollout**.
3. Give it a comment window (usually 3 working days). Anyone can weigh in.
4. A maintainer records the decision. If accepted and architectural, add an [ADR](../adr).
5. Then build.

## Good RFCs
- State the decision up front, then justify it.
- List the alternatives you rejected and why — that's the real content.
- Small enough to read in five minutes.
